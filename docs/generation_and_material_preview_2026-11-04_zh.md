# 生成阶段的稀疏化与材料颜色编辑预览

日期：2026-11-04。用户澄清：最初提出的三角形粗细分配希望用于Mesh生成/构建，
不应在整理方法时仅保留为下游后处理。该目标予以保留，以下区分目标与现有代码。

## 1. 稀疏化的位置

用户期望研究的流程是：图像→初始粗几何→粗部件/材料/接口候选→分配局部
几何预算→构建最终Mesh→精细物理推断及编辑。平坦同材质区域少面，薄结构、
接口与可靠材料边界更多面。早期未知的内部参数只作为带来源候选，不当真值。

与目前已实现的“完整Mesh→普通QEM→更少面数”区分。后者可做基线和开发验证，
不证明节省了InstantMesh初次生成成本。如果InstantMesh仍完整解码原网格，随后
重网格化属于后处理或最终几何优化，不能仅改名称成为生成阶段加速。

真正的构建阶段研究需要能访问并修改几何场的采样、网格提取或局部细化过程。
先检验预训练前端能否输出可用的粗几何/场，局部提取是否兼容，并检查细粗网格
过渡的裂缝、退化、拓扑和薄结构；不能假定修改分辨率就能保持预训练结果。

基础方法可参考[FlexiCubes](https://research.nvidia.com/labs/toronto-ai/flexicubes/)
和[SparseFlex](https://arxiv.org/abs/2503.21732)。它们已有可微/自适应/稀疏网格
表示，因此拟议差异应来自部件、接口与物理任务如何决定预算，并用实验支持。
不要求从零训练整个单图三维生成模型，也不能将已有算子串联宣称原创。

评价区分初次构建、后续物理处理和编辑；分别记录真实面数、采样/网格单元数、
预处理与提取耗时、总耗时、内存以及几何/物理/接口误差。
若高分辨率物理场已先算完，它不能作为初次构建省计算的免费输入。

## 2. 第一版应用呈现

图片进入系统后形成三维对象与部件。用户点选部件或使用明确部件名称，选择
材料预设，先用代表颜色反馈；再在物理域可用时执行材料或构造编辑，更新质量、
质心、惯量，导出新资产。颜色预览、真实PBR外观、内部构造和物理推断分别标记。

示例选择已有ABO-500蓝色脚凳`B082VML3QJ_ATVPDKIKX0DER`。原图是该数据集
的第0视角，参考Mesh来自此前已下载的原生GLB，没有运行InstantMesh。

预览目标为木质底架和腿这一组表面。先采用此对象特定的颜色+高度规则，面掩码
可审计，不冒称自动精细语义分割或独立制造部件拆分。颜色只是材料选项的示意，
不代表材料固定具有该颜色，也不表示新材料满足原连接或承载要求。

| 选项 | 显示颜色 | 指定密度示例kg/m³ |
| --- | --- | ---: |
| 木材 | 原始纹理近似色／棕色图例 | 650 |
| 铝材 | 银灰色 | 2700 |
| ABS塑料 | 橙色 | 1050 |

这些密度是设计输入，不是该ABO样本的测量或VLM预测。只在目标材料实心体积
保持不变时，目标区域质量比例等于密度比例。图中的4.15倍、1.62倍不代表整个
脚凳质量变化；原Mesh开放且真实内部未核验，因此不填绝对质量。

## 3. 已执行入口

```bash
python scripts/preview_material_edit.py
```

默认读取`data/material_color_demo/source.png`和`camera.json`，它们由已有数据集
视图及对应相机复制而来，来源记录在同目录`source.json`。GLB默认路径是
`data/abo500_ten/B082VML3QJ_ATVPDKIKX0DER/model.glb`。
可用`--mesh`、`--image`、`--camera`、`--output`指定输入和新目录。

保存原色、铝材色和ABS色PLY，目标面掩码、报告、PNG/SVG/PDF。报告记录源图、
网格与相机哈希、选择规则及轮廓重叠。视图使用相同相机及深度测试，不直接
涂改原始图片；Mesh颜色按面近似，尚无完整纹理PBR重渲染。
显示时对所有面板使用共同裁剪范围，原始图像文件保持原样。

原网格10460面，其中目标972面。运行中检查顶点、三角面与非目标面颜色保持
一致。当前为颜色预览，报告`physics_committed=false`，尚未将此物体重建为
编辑引擎所需的内部体积状态。它不取代此前已通过解析验证的物理编辑演示。

最终实际输出为`outputs/material_color_preview_20261104_v3/`。相同数据相机下
参考Mesh与输入alpha轮廓IoU为0.99018；可见像素改变范围也检查为目标面投影内。
此项检查只支持展示对应关系，不构成未知几何或物理属性的准确性证据。
新增两个Python文件通过88列E/F/I检查，CLI完成并人工检查最终PNG布局。
